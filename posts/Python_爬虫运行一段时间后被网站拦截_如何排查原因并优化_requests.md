# Python 爬虫运行一段时间后被网站拦截：如何排查原因并优化 requests 爬虫？


> **TL;DR**:Python 爬虫运行一段时间后被拦截，通常不是单一原因，而是请求频率、IP 信誉、Headers/Cookie 异常、会话行为不自然或触发验证码共同导致。排查时应先确认拦截表现和状态码，再从频率、身份伪装、代理质量、登录态和动态反爬逐项定位，并用限速、重试、会话管理和合规策略优化。


## 为什么 Python 爬虫运行一段时间后才会被网站拦截？

Python 爬虫刚开始正常、运行一段时间后才被拦截，通常是因为网站风控系统根据“累计请求行为”识别出了自动化访问。单次请求看起来可能正常，但连续 5 分钟每秒访问 2 次、固定访问同一接口、请求间隔总是 1.000 秒，就会形成明显的机器特征。

### 常见拦截表现

运行一段时间后失败，不一定都是 IP 被封，常见表现包括：

- HTTP 403：服务器拒绝访问；
- HTTP 429：请求过多，触发限流；
- 302 跳转到验证码页或登录页；
- 页面正常返回，但列表为空、价格为空、字段缺失；
- 连接重置，例如 `Connection reset by peer`；
- 登录态失效，需要重新登录；
- 接口返回风控码，例如 `risk_control`、`verify_required`、`access_denied`。

### 反爬看的不是一个 User-Agent

User-Agent（浏览器身份字符串）只是最基础的特征。实际反爬更常结合 IP 频率、Cookie（网站保存的会话标识）变化、账号行为、访问路径、Referer、请求头完整性、验证码触发次数等判断。

`requests` 爬虫默认行为也容易暴露自动化特征：没有浏览器指纹（浏览器环境特征，如屏幕、字体、JS 执行能力）、不会自动执行 JavaScript、请求间隔过于规律、复用 Cookie 不完整。短期封禁、IP 限流、账号风控、Cookie 过期和验证码拦截，本质上都是网站对异常访问行为的不同处置。

## 如何先判断爬虫是被反爬拦截还是代码本身出错？

判断方法是：先看完整 HTTP 证据链，而不是只看 Python 是否抛异常。HTTP 状态码（服务器返回的结果编号）、响应正文、响应头、跳转链都要记录；很多反爬不会让 `requests` 报错，而是返回 403、429、验证码 HTML 或跳转到登录页。

| 现象 | 可能原因 | 排查动作 |
|---|---|---|
| 403 Forbidden | 权限不足、Headers 指纹异常、IP 被拒 | 对比浏览器与 `requests` 的 User-Agent、Referer、Cookie |
| 429 Too Many Requests | 请求频率过高、触发限流 | 降到每 5-10 秒 1 次，观察是否恢复 |
| 302 跳转 | 登录失效、验证码、人机校验 | 打印 `response.history` 和最终 URL |
| 200 但内容异常 | 返回空页、风控页、假数据 | 保存响应正文前 500 字符并搜索“captcha”“verify” |
| 超时/连接失败 | 代理不稳定、网络问题、目标站阻断 | 记录代理 IP、耗时、失败时间点 |

### 对比三种访问结果

用浏览器、`curl`、Python `requests` 访问同一个 URL。如果浏览器正常、`curl` 正常、只有 `requests` 异常，优先查 Headers、Cookie 和会话；如果三者都失败，可能是 URL、参数或目标站本身变化。

### 记录最小排查日志

每次失败至少记录：请求 URL、查询参数、Headers、Cookie、代理 IP、响应状态码、响应耗时、失败发生在第几分钟或第几次请求。再用小样本低频复现，例如只请求 20 次、每次间隔 10 秒；若低频正常、高频失败，基本可判断与频率或运行时长相关。

## 如何排查 Python requests 爬虫最常见的拦截原因？

排查 Python requests 爬虫被拦截，应按“频率/IP → Headers → Cookie/Session → 动态参数”的顺序逐项验证。先看日志中 403、429、302 到验证码页、响应内容变空等现象，再对照请求特征定位。

### 1. 请求频率和访问路径

检查是否并发过高、间隔过短，例如 1 秒内连续请求 10 次、固定每 0.5 秒访问一次、按 `page=1,2,3...` 机械翻页。低级反爬通常会直接根据请求频率、单 IP 请求量、路径规律触发限制。

### 2. Headers 是否像正常浏览器

Headers（HTTP 请求头，用来描述客户端身份和偏好）缺失时很容易暴露脚本。重点检查 `User-Agent`、`Referer`、`Accept-Language`、`Accept`、`Connection`。例如只带默认 `python-requests/2.x`，通常比 Chrome 浏览器请求更容易被拦截。

### 3. Cookie、Session 和登录态

Cookie（网站保存在客户端的会话信息）和 Session（requests 中复用连接与 Cookie 的会话对象）不稳定，会导致“刚开始正常，过一会儿失效”。检查 Cookie 是否过期、登录态是否需要刷新、是否每次请求都新建连接，建议用 `requests.Session()` 维持状态。

### 4. IP、代理和动态参数

如果单 IP 请求量过大，或代理池大量使用数据中心 IP，容易被标记。还要检查接口是否需要 `token`、签名、时间戳、`csrf`（防跨站请求伪造的校验参数）或 JS 加密参数。低级反爬看频率、IP、Headers；高级反爬还会看 JS 指纹、鼠标轨迹、验证码、设备环境，单靠 requests 伪装请求头通常不够。

## 如何优化爬虫策略以降低被拦截概率？

降低 Python requests 爬虫被拦截概率的核心，是把“高频、固定、无上下文”的请求，改成“限速、随机、可恢复、可观测”的访问策略。比如不要每秒固定请求 10 次，而是设置 1～3 秒随机延迟；遇到 429 Too Many Requests（请求过多）时暂停 60～300 秒，而不是立刻重试。

### 优化清单

- **限速**：控制 QPS（每秒请求数），例如单域名 0.5～2 QPS。
- **随机延迟**：使用 `random.uniform(1, 5)`，避免固定节奏。
- **Session**：使用 `requests.Session` 复用 TCP 连接并保留 Cookie（网站识别用户状态的小型数据）。
- **日志**：记录 URL、状态码、响应长度、重试次数，方便定位 403、429、5xx。
- **重试**：对 5xx（服务器错误）可退避重试；对 403（禁止访问）应暂停并检查身份、Cookie、IP。
- **代理质量控制**：剔除超时、重复、被封 IP，避免低质量代理池加速封禁。
- **缓存**：对不常变化页面落盘缓存，减少重复抓取。
- **断点续爬**：保存已抓 URL 或分页游标，异常后从中断位置继续。
- **robots.txt 合规检查**：先查看站点抓取规则，避免访问禁止路径。

Headers（请求头，描述客户端信息）要与真实浏览器一致即可，例如 `User-Agent`、`Accept-Language`、`Referer`，不要盲目堆砌几十个字段。优先使用官方 API、开放数据接口或本地缓存，通常比反复抓 HTML 页面更稳定，也更合规。

## 如何设计一个更稳定、可观测、合规的 Python 爬虫？

更稳定的 Python 爬虫，应当把“请求成功”升级为“可限速、可重试、可暂停、可追踪、可合规”的任务系统。不要只在 `requests.get()` 外层套循环，而要记录成功率、失败率、状态码分布、代理命中率、平均响应时间等指标，便于判断是网站风控、代理失效，还是解析代码异常。

| 模块 | 作用 | 建议实现 |
|---|---|---|
| 限速模块 | 控制访问频率 | 每个域名设置 1～5 秒间隔，遇到 429 自动降速 |
| 重试模块 | 处理临时失败 | 对超时、502、503 重试 2～3 次，403 不盲目重试 |
| 代理模块 | 降低单 IP 压力 | 记录代理成功率、失败率、响应时间，淘汰低质量代理 |
| 日志模块 | 定位问题来源 | 记录 URL、状态码、异常类型、耗时、代理 IP |
| 缓存模块 | 避免重复请求 | 已抓取 URL 写入 SQLite、Redis 或本地文件 |
| 合规模块 | 控制采集边界 | 检查 robots.txt、服务条款、版权和隐私要求 |

### 建立失败分类和熔断机制

失败不要只打印 `error`。建议分为网络错误（超时、连接失败）、解析错误（HTML 结构变化）、权限错误（401、403）、风控错误（429、验证码页）。当连续出现 5 次以上 403/429 时，触发熔断机制（自动暂停或降速），例如暂停 10～30 分钟，而不是立刻高频重跑。

### 使用队列和断点续爬

任务队列（把待抓 URL 按状态管理的机制）可以记录 `pending / success / failed`，配合断点续爬避免程序崩溃后从头请求。合规上，应避免绕过登录、验证码、付费墙等强访问控制，不采集敏感个人信息。

## 常见问答(FAQ)

**Q:Python requests 爬虫返回 403 一定是 IP 被封了吗？**

A:不一定。403 只表示服务器拒绝访问，可能是 IP 信誉差，也可能是 Headers 缺失、Cookie 失效、Referer 不对或访问路径异常。建议先对比浏览器请求，再检查状态码、响应内容和请求头差异。

**Q:爬虫被 429 限流应该怎么处理？**

A:429 通常表示请求过快，应优先降频而不是继续重试。可以把间隔从 0.1 秒提高到 2-5 秒，加入随机 sleep、指数退避，并遵守 Retry-After 响应头，避免短时间集中访问同一接口。

**Q:给 requests 加 User-Agent 就能解决反爬吗？**

A:不能。User-Agent 只能解决最基础的识别问题，很多网站还会检查 Accept、Referer、Cookie、请求顺序和行为节奏。比如只改 UA 但没有登录 Cookie，访问会员页仍然可能返回 403。

**Q:使用代理池是否一定能避免 Python 爬虫被拦截？**

A:不能。代理池只能分散 IP 风险，无法修复高频请求、异常 Headers 或无效登录态。低质量代理还可能因共享滥用更容易被封。应同时控制频率、维护 Session，并选择稳定、合规的代理来源。

**Q:爬虫遇到验证码应该怎么办？**

A:遇到验证码说明已触发更强风控，应先降低频率、减少并发，检查是否违反网站规则。不要盲目绕过验证码，可改用官方 API、申请数据授权，或在允许范围内采用人工验证流程。
